# Solv-In

AI-assisted Property & Casualty (P&C) insurance claims platform.

## Current development stage

Phase 1 foundation and dashboard are in place. Phase 2 adds a working claims register and First Notice of Loss (FNOL) workflow.

### Stack
- Angular + TypeScript frontend
- Python + FastAPI backend
- MongoDB database
- Gemini Vision integration for preliminary image damage analysis

## Phase 2 functionality
- Create Property and Casualty claims through the FNOL form.
- Generate sequential claim IDs in the format CLM-YYYY-000001.
- Save claim records in MongoDB.
- Search claims by claim ID, customer or policy number.
- Filter claims by type and status.
- Update claim workflow status.
- Show dashboard counts from MongoDB when connected.

## Run locally

Prerequisites: Node.js LTS, npm, Python 3.11+, MongoDB Community Server.

### Backend (Windows PowerShell)
```powershell
cd solv-in/backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env
uvicorn app.main:app --reload
```

API documentation: http://127.0.0.1:8000/docs

### Frontend (new terminal)
```powershell
cd solv-in/frontend
npm install
npm start
```

Open http://localhost:4200.

## Important safeguards
- Use fictional data only during development.
- AI assessments are preliminary and require authorised human review.
- No automatic claim approval, rejection or settlement.
- No final coverage, liability or fraud decisions.
- Do not invent missing claim facts or policy terms.
- Financial calculations must use deterministic Python Decimal logic and verified policy terms.
- Never commit .env files or API keys.
- This is a development build, not production-ready. Authentication, role-based access control, tenant isolation, secure document storage and audit logging remain future requirements.


## Phase 3 – Authentication and role permissions

- JWT bearer-token login with a short configurable token lifetime.
- Password hashing using Argon2 through pwdlib.
- Active-user lookup on every authenticated API request.
- Protected claim and dashboard APIs with role-based permissions.
- Super Administrator-only user creation and user listing until insurer tenant isolation is implemented.
- Angular sign-in/sign-out and session-scoped token storage.

### Configure the first administrator

1. Copy `.env.example` to `.env` in `solv-in/backend`.
2. Set `JWT_SECRET_KEY` to a randomly generated secret of at least 32 characters. For example, use Python: `py -c "import secrets; print(secrets.token_urlsafe(48))"`.
3. Set a unique `INITIAL_ADMIN_EMAIL` and a strong `INITIAL_ADMIN_PASSWORD` (at least 12 characters, with letters and numbers).
4. Start MongoDB, then start FastAPI. On first startup, the configured account is created as the Super Administrator if that email does not already exist.
5. Sign in through the Angular application with those credentials.

Do not commit `.env`, credentials, JWT secrets or real customer data.

### Current role boundaries

The API recognises: Super Administrator, Insurance Company Administrator, Claims Manager, Property Adjuster, Casualty Adjuster, Surveyor, Actuarial Analyst, Approver, Auditor and Customer.

The current implementation grants claim read access to operational roles, claim creation to administrators/managers/adjusters, and status updates to administrators/managers/adjusters/approvers. User provisioning is restricted to the global Super Administrator. Customer self-service, claim ownership scoping, insurer/tenant isolation, adjuster claim-type scoping, password reset, MFA, refresh-token rotation and audit logging are not implemented yet. Do not use this build for production or real customer information.

 
## Phase 4 – AI-assisted visual damage analysis

- Authenticated users with an operational claims role can upload JPG, PNG or WEBP evidence (maximum 10 MB).
- Gemini Vision returns preliminary visible observations, affected areas, a qualified possible cause, severity, confidence, limitations and recommended next steps.
- Assessments are saved in MongoDB in the `damage_assessments` collection and can be linked to an existing Claim ID.
- Repair costs are deliberately not generated by the model. No dimensions, quantities, coverage, liability, fraud or final claim decision are inferred.
- An authorised adjuster must verify the assessment before it is used in claim handling.

### Configure Gemini
1. Add your Gemini API key to `backend/.env` as `GEMINI_API_KEY=your_key`.
2. Optionally set `GEMINI_MODEL=gemini-2.5-flash`.
3. Install the updated backend requirements and restart FastAPI.
4. Sign in, open **AI Damage Analysis**, select an image, optionally enter a Claim ID, and run the analysis.

Never commit the API key or upload real policyholder evidence to an unapproved environment. This remains a development feature and requires privacy, security, model-quality and human-review testing before production use.


## Phase 5 – Claim-linked assessment review workflow

- Retrieve all saved AI damage assessments using an existing Claim ID.
- Keep the assessment status separate from the overall claim status.
- Record review history with reviewer email, role, timestamp, decision and notes.
- Adjusters and surveyors can mark an assessment reviewed or request more evidence.
- Claims managers, insurer administrators and authorised Approvers can approve or reject the assessment; notes are mandatory for a rejection or evidence request.
- This approval applies only to the AI assessment record. It does not approve, deny or settle the insurance claim.
- The Gemini API key remains optional for development of the review workflow; image analysis itself requires the key.


## Phase 6 – Claims financial calculation engine

- Calculate repair line items in Python using `Decimal` arithmetic and half-up rounding to two decimal places.
- Capture quantity, unit, verified unit rate, taxable status and depreciation for each repair item.
- Support multiple configurable tax components (state, local or other jurisdictions), each with its own rate, tax base and authority reference. Tax rates are entered from a verified schedule; the application does not assume a universal state tax rate.
- Support documented fees/other charges, policy deductibles and optional simple interest on actual days/365.
- Interest is excluded by default. To include it, the user must explicitly enable it and supply the rate, principal, day count and policy/legal authority reference.
- Require a pricing source and effective date; estimates are linked to a Claim ID and saved in MongoDB `financial_estimates`.
- The estimate is marked **Preliminary – Pending Review**. It does not determine coverage, liability, claim approval or settlement.
- API: `POST /api/claims/{claim_id}/financial-estimates` and `GET /api/claims/{claim_id}/financial-estimates`.
- Run calculation tests from `solv-in/backend` with `pytest`.

### Worldwide jurisdiction and currency support

- Claim intake captures the loss country using ISO 3166-1 alpha-2 and the claim currency using ISO 4217; neither is silently defaulted to India.
- Financial estimates capture country, state/province/territory, region, locality, postal code, loss date and a separate tax-point date.
- ISO country and currency codes are validated against maintained reference datasets.
- Currency rounding precision is obtained from Babel/CLDR currency metadata (for example, zero decimal places for JPY and three for KWD), rather than assuming two decimals for every currency.
- Add up to 20 independent tax components for national, state/provincial, regional, municipal or other applicable jurisdictions. Each component has a tax type, jurisdiction, rate, taxable base, optional compounding on prior taxes, effective dates and authority reference.
- Interest supports selectable simple-interest day-count conventions (Actual/365, Actual/360, Actual/366 and 30/360), but remains disabled unless the applicable policy or law supports it.
- The system does not perform foreign-exchange conversion. All line items, fees, taxes, interest and deductible in one estimate must be expressed in the claim currency.
- Global tax rates and legal rules are not preloaded or guessed. They must be supplied from verified, current sources for the correct jurisdiction and tax point. Complex rules such as exemptions, thresholds, tax-inclusive pricing, reverse charge, special insurance premium taxes, multiple tax registrations and country-specific rounding may require additional jurisdiction-specific rule modules before production.

This is a globally extensible calculation framework, not a substitute for local tax/legal advice or a live worldwide tax-compliance database.



## Phase 7 – Global Tax Rules Database

Solv-In now includes a configurable tax-rule registry for jurisdiction-specific tax profiles. Administrators can create draft rules with ISO country/currency codes, administrative area, region/locality, tax name/type, rate, taxable base, compounding, tax-point description, effective dates, and authority/source references. Only authorised administrators can activate or deactivate rules. Active rules are immutable; create a new version rather than editing a rule already in use.

The claim lookup endpoint `GET /api/claims/{claim_id}/applicable-tax-rules?tax_point_date=YYYY-MM-DD` returns active rules matching the claim country, currency, jurisdiction and effective date. It prefers more specific jurisdiction matches and flags same-specificity duplicates as ambiguous. If no verified rule matches, it returns `No verified matching tax profile`.

**Important:** This is a rule registry and matching framework, not a preloaded global tax database or legal/tax advice. Rates must be verified against official authorities before activation. No rates are invented or automatically scraped. The existing financial estimate calculator remains a separate calculation workflow; rule lookup is advisory and does not silently add taxes to an estimate.


## Phase 8 – Automated tax calculation and financial estimate integration

- Financial estimates default to **automatic tax mode**. The API matches active tax rules by claim country, currency, administrative area, region/locality and tax-point date.
- Matching rules are converted into deterministic Python Decimal tax components and calculated using each rule's configured taxable base, compounding setting and explicit calculation order (lower order runs first).
- The saved estimate contains exact rule identifiers, versions, jurisdiction, rate, effective dates, authority references, source URLs and verification metadata as an audit snapshot.
- Conflicting active rules for the same tax at the same jurisdiction specificity stop automatic calculation with a conflict response. Administrators must resolve the tax registry instead of allowing Solv-In to guess.
- If no active verified rule matches, the estimate is still preliminary but explicitly marked **No verified matching tax profile**. No rate is assumed; the warning requires human review before approval.
- A deliberate **manual tax mode** is available for authorised staff using an approved external tax schedule. Such estimates are labelled **Manual tax override - verify before approval** and are not represented as registry-verified.
- API: the existing `POST /api/claims/{claim_id}/financial-estimates` endpoint applies verified registry rules automatically by default and stores rule snapshots with the result.

Automatic tax application is limited to tax components and taxable bases represented by the configured rule model. It is not a worldwide tax-compliance engine; exemptions, thresholds, tax-inclusive pricing, reverse charge, special insurance taxes and local filing/reporting obligations require separately verified jurisdiction-specific logic.
